# Authenticated signalling preparation

Status: protocol and bounded coordinator source prepared. The database authority reader, network runtime and real WebRTC integration remain pending. No connection or command authority is granted by these modules.

The protocol has separate P-256 browser admission and role-specific RTC transcript domains. Browser admission uses a fresh server-owned transport UUID and a maximum 8,000 ms challenge. This UUID is separate from browser enrollment proof IDs. Account identifiers remain text. Nonces are exactly 32 cryptographically random bytes encoded as canonical, unpadded base64url. All timestamps are integer Unix milliseconds.

The strict RTC binding contains the browser P-256 public key and thumbprint, Connector Ed25519 SPKI and fingerprint, farm/agent/browser-key IDs, account ID, credential jti, transport UUID, both nonces, authoritative origin/audience, both DTLS SHA-256 fingerprints, and SHA-256 hashes of the exact UTF-8 final offer and answer SDP bytes. No line-ending normalization occurs. Connector creates the offer; browser creates the answer. A changed description requires a new transport context and proofs.

Signature bytes are UTF-8 of `Open3DFarmManager/rtc-session-proof/v1\0`, the literal role (`browser` or `connector`), `\0`, and canonical JSON of the strict binding. Browser signatures use ECDSA P-256/SHA-256 in 64-byte WebCrypto/P1363 format. Connector signatures use Ed25519. Both use canonical unpadded base64url. `BrowserRtcProof` and `ConnectorRtcProof` parse strict role-specific envelopes. The real Connector adapter must sign through its encapsulated identity; the portable CryptoKey primitive does not authorize private-key export.

Endpoints must compare their exact local/remote descriptions and the actual negotiated DTLS certificate against the authenticated binding. The protocol helper checks description bytes and pins; it cannot inspect a live DTLS certificate. A server-supplied frame or UUID alone is never an admission result.

The proposed prototype policy has an 8-second admission deadline and a separate, maximum 30-second read-only transport lifetime, further capped by current session and credential deadlines. Both endpoints must independently enforce local monotonic deadlines and reject late asynchronous callbacks after closure. Proof freshness permits admission; a consumed proof is not continuing authority. Passive server revalidation must not renew the login session or transport lifetime. The coordinator requires an independently enforced monotonic endpoint timer through its trusted adapter port. Real endpoint timer enforcement remains pending adapter integration.

`commands_enabled` is always false for every identity. This includes UUID-compatible accounts. No command authorization, status, camera or command payload travels through the server signalling frame protocol. It accepts bounded SDP, direct ICE and close metadata only; relay/TURN candidates are rejected. A later integration must retain Connector safety and close into read-only behavior on expiry or failed current-state authorization. Remote revocation cannot be learned immediately by an offline Connector and does not stop an ongoing print.

Focused validation: four real crypto/protocol tests passed under Node and Bun, covering both algorithms, cross-domain/role rejection, identity/context mutation, exact SDP mutation with unchanged certificate, strict limits and forbidden frames. Eight coordinator tests also passed under Node and Bun with real signatures and an explicitly synthetic credential/authority gateway. They cover metadata relay, fixed lifetime, revoked snapshots, clock regression, bad signatures, allocation and queue limits, timer cleanup and late asynchronous results. Focused strict TypeScript checks passed. Actual database reads, current-state PostgreSQL revocation races, network runtime admission, real endpoint deadlines and native WebRTC behavior remain unvalidated here. No new grants, schema, HTTP routes or runtime wiring were added. A current-head integrated gate remains pending.

The coordinator admits only opaque server-created endpoint handles. It generates the transport UUID; received frame identifiers never create authority. Its trusted reader port must validate the independent current login session, farm membership, approved browser key, enrollment and issued credential, without touching session activity. Its credential gateway uses the existing one-use `signalling` proof methods and matches exact server context, jti, key, origin and audience. Neither reader nor gateway test doubles are production authorization wiring.

Limits are 64 allocated contexts, two per browser key, four per Connector agent, 32 in-flight authority reads and 32 in-flight proof/crypto operations. In-flight slots remain occupied until the underlying work settles even after context closure. There is no unbounded retry queue. Each endpoint has at most eight queued frames; aggregate queued data per context is at most 32 KiB, plus one bounded in-flight frame. ICE has a 64-candidate limit per endpoint. One Connector offer and one browser answer are accepted. Queue overflow closes the context. A bad proof closes its ephemeral context; the Connector gateway still enforces its own persisted attempt policy. Passive checks occur every five seconds and never extend either deadline. Context closure cancels timers, drops queued data and token references, removes handles, and invalidates all late results.

The next integration must implement and review a least-privileged PostgreSQL current-authority reader, its exact row-lock order and grants, then wire trusted sockets and endpoint adapters. The reader must include current session policy and credential expiry in `validUntil`, serialize against session/membership/browser/enrollment revocation, and preserve the established enrollment-before-credential lock order. No proposed grant was executed in this slice. Transport binding delivery only configures the expected read-only transcript; endpoints must still prove both real keys and match the actual negotiated DTLS certificate before accepting P2P data.
