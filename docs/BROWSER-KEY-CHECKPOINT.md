# Browser key persistence checkpoint

Review of the Phase 0 task list identified E2.3.2 as a bounded continuation of the existing E4.3.2 signature implementation. Independent login, registration and device revocation still require server integration; they are not simulated as working product features here. No original private planning documents or deployment details are reproduced.

## Completed local flow

The browser-only `app/utils/device-key.ts` uses the existing protocol's WebCrypto P-256 generator and native IndexedDB to retain a nonextractable private key. Keys are scoped by farm and user IDs supplied by a future authenticated caller. This scope is storage organization, not an access-control boundary against same-origin JavaScript.

A read/write transaction chooses one winner when tabs generate candidates concurrently. The helper returns only after transaction completion, checks stored algorithm/usages/extractability and verifies that the private/public pair matches. Invalid records and unavailable storage fail with a fixed error. It never overwrites a corrupt record or falls back to an ephemeral key. The browser APIs follow the documented [IndexedDB transaction lifecycle](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction) and [CryptoKey properties](https://developer.mozilla.org/en-US/docs/Web/API/CryptoKey); no new dependency or cryptographic format was introduced.

The existing Chromium-to-Node signature test now persists a key, reloads the page, confirms the same public JWK, confirms private export is denied, signs a synthetic command and verifies acceptance once followed by replay rejection in Node. Other browser tests cover simultaneous tabs, separate scopes, inconsistent key pairs, denied storage and aborted insertion. The original homepage/hidden-route test remains in the suite.

## Boundaries and next dependencies

- No route or UI automatically invokes key creation. A future enrollment flow must use authenticated farm/user IDs and explicitly register the public key before any device is trusted.
- No server registration, device identifier assignment, account authorization, remote revocation, WebRTC or printer dispatch is supplied by this helper. Node verification in the browser test uses synthetic trusted context.
- Clearing browser storage or browser eviction loses the key. The future registration flow must detect that it differs from an enrolled public key and require enrollment again; it must not silently replace server trust. Browser persistence is not a backup or a crash-durability guarantee.
- A nonextractable key still permits hostile same-origin JavaScript to request signatures. CSP, XSS prevention, authenticated UI state and server/Connector authorization remain necessary.
- Chromium was verified locally. Other browsers, private browsing behavior, blocked upgrades and actual quota exhaustion remain unverified. Failure injection covers a denied open and aborted insert, not every browser failure mode.

The broader review still leaves E1.2 database/migrations and E2.1 login as dependencies for pairing, agent ingestion and device registration. Existing telemetry decoders and queue have local integration tests, but authenticated ingestion and outage-drain acceptance require their server endpoints. E0 simulator acceptance and the network/WebRTC scenarios remain behind the pending container permission. This checkpoint closes a local persistence/signing flow, not Phase 0 or the complete device-management feature.

## Durable internal browser-device registry

This section supersedes the earlier absence of server registry storage only. The preceding browser-helper account remains historical evidence. Enrollment endpoints are still absent, and existing command tests still supply synthetic trusted context; this registry does not turn that context into authenticated transport or dispatch.

Migration `0013_browser_device_registry` and `PostgresBrowserDeviceRegistry` add an internal PostgreSQL registry. This slice does not expose enrollment or approval endpoints and does not alter authentication runtime or the IndexedDB helper. Callers must obtain the internal login session reference from the reviewed host-only sealed-cookie flow; passing a reference or a JWT to this internal class does not authenticate a browser.

The protocol accepts exactly the four public JWK members `kty`, `crv`, `x`, `y`. A caller exporting WebCrypto JWKs must deliberately select those public members, rather than send `ext`, `key_ops` or private parameters. Canonical 32-byte coordinates are checked and native P-256 import rejects invalid curve points. The RFC 7638 SHA-256 thumbprint and the immutable farm/account/key association identify an enrollment. No dependencies were added.

A durable challenge binds configured origin, audience, purpose (`enroll` or `recover`), account, farm, key, a random nonce and a 60-second validity window. Signatures use domain-separated canonical JSON and WebCrypto's P1363 ECDSA encoding. Its public `session_id` is a fresh UUID separate from the internal login session reference; the database retains that association privately. A challenge can be consumed once, including an invalid signature. Replays, expiry, current session/account revocation and inactive farm membership fail closed. Transactions lock and revalidate current account, session and membership rows, then key/challenge state; approval and revocation acquire both actor and owning account/session scopes in deterministic identifier order; storage failures never authorize.

Enrollment initially creates an unproven pending key. Successful possession proof alone never approves it. An explicit current owner/admin approves a proven key, and its owning account, membership and originating login session must still be valid. Human approval may occur after the 60-second challenge window: the proof must have been consumed successfully inside that window, but the durable successful result remains approvable while those current authorization checks hold and the immutable 24-hour pending-registration lifetime has not elapsed. Reproof never extends that lifetime. A new login session can use `recover` to prove the same existing key again. A lost key requires a new key, fresh proof and explicit approval; it does not replace or resurrect the old enrollment. Revocation is terminal and requires current actor owner/admin membership; an administrator can revoke a key after its owner's membership has been removed.

`authorizeDevice` supplies only an internal snapshot for a future authenticated WebRTC lease issuer. It requires a current login session/account/membership, an approved key and a fresh successfully consumed proof associated with that login session and its public proof-session UUID. It returns the current membership role, not a role frozen at approval. Its deadline cannot exceed the original proof expiry or login session expiry. A future transport issuer must separately create and authenticate a transport-session identifier; the proof-session UUID is not that identifier. The UUID projection helper only checks existing account and separately issued transport-session identifier shapes; it does not authenticate or issue command context. Legacy text account identifiers remain enrolled as text and fail command UUID projection explicitly. Login references are never projected into public command session identifiers.

Runtime and reader database roles have distinct capabilities, without login, schema creation, role escalation, membership mutation or deletion. Database triggers retain tombstones, immutable identity bindings, approval attribution and terminal revocation. Native cryptographic validation belongs to the registry boundary; SQL structural checks do not independently prove an elliptic-curve point or thumbprint. The application SQL role is a trusted service capability, not an untrusted browser capability.

This internal implementation has conservative fixed limits: 10,000 retained keys globally, 128 per account, 32 per account/farm, 30,000 retained challenges and three lifetime challenges per key, counting failed and expired attempts. Only one unexpired unconsumed challenge per key is allowed. Exhaustion fails closed and requires a separately reviewed retention/recovery policy; this is not a production lease-renewal service. A single transaction advisory lock serializes the bounded registry. Statement and lock deadlines limit contention. No HTTP mutation or recovery UX, lease signing/distribution, WebRTC wiring, browser-to-Connector command dispatch, command fallback or immediate offline revocation is implemented. Previously issued authorization can remain usable until its future lease deadline.

Migration acceptance must apply the real contiguous sequence including separately owned `0011` and `0012`. Isolated application of `0013` after existing prerequisite tables is partial database evidence only; no fake migration journal or backfill is acceptable. Full Phase 0 still requires authenticated browser integration, signed pause, tamper/replay/revocation rejection, outage recovery and simulator/WebRTC acceptance.

Focused validation passed: three Bun protocol tests (32 assertions), one Chromium WebCrypto-to-server proof test and 17 named PostgreSQL integration groups. Database coverage includes real proof/race/replay, recovery/expiry, scope and terminal revocation, owner/admin approval, distinct actors and current roles, opposite concurrent approvals, wrong-key attempt consumption, session/account/membership revocation, post-lock revocation and expiry, owning membership, exact deadlines, pending-registration lifetime, allocation/attempt limits, immutable tombstones and restricted roles, and closed-database failure. A fresh database connection retained replay and revocation decisions; this is not process or PostgreSQL restart evidence. The Chromium test does not verify a bundled browser protocol module.

These PostgreSQL checks applied `0001`–`0011` plus `0013` directly in an isolated synthetic database without a migration journal. The missing `0012` still blocks official contiguous-migration acceptance. Coordinator `bun run check:all` passed formatting and type checks, with 218 Bun tests passing and one migration-catalog test failing because `0012` is missing. Separately, all 107 Node tests and the build passed. Official contiguous-migration acceptance remains pending `0012`.
