# Read-only Moonraker client checkpoint

This slice adds an actual HTTP and WebSocket connection lifecycle behind a provisional Connector-only API. It is not wired into the CLI or farm configuration. The 0015 printer ownership key is data, not a network location. Registration, the trusted local assignment loader and its endpoint allowlist still need an agreed integration contract.

`createMoonrakerSubscription({ assignment: { printerKey, origin }, allowedOrigins, limits, onEvent, signal })` validates the assignment and limits before network access. Printer keys retain their exact value. Origins must be origin-only HTTP(S) values with no credentials, controls, query, fragment or other path. The normalized origin must exactly match the separately supplied local allowlist. These inputs must come from trusted local configuration, never browser-provided URLs. The function returns `{ done }`; abort ends its application lifecycle. The callback must return synchronously with `undefined`. A throwing or asynchronous callback ends the subscription and rejects `done` without queuing more work.

The client issues only a fixed `GET /server/info`, with HTTP redirects disabled, and `printer.objects.subscribe` on the derived `/websocket` endpoint. Subscription fields are `webhooks.state`, `print_stats.state` and `virtual_sdcard.progress`. There is one outstanding RPC request with a fixed ID on each new socket, no generic RPC dispatcher and no commands. This local printer connection does not add a browser backend proxy, command fallback or cloud telemetry transport.

The subscription result supplies the complete baseline. Selected fields from validated `notify_status_update` deltas merge into that baseline and pass through the existing parser. Duplicate JSON fields, remote errors, mismatched or repeated replies, premature status notifications, invalid selected fields and conflicting equal source timestamps invalidate the connection. Older updates and exact repeats do not refresh freshness. Newer selected-field updates can refresh freshness without emitting duplicate normalized state. Unselected fields never enter the baseline. Source time is Klipper's monotonic clock, not wall time.

Disconnect, invalid data and readiness changes clear the baseline. Each reconnect repeats readiness and subscription, accepts a fresh snapshot and resets the source clock. A fresh snapshot after an unavailable transition is deliberately emitted even when its state matches the previous connection. There is no durable event identity or queue integration in this slice. Retry delays stay within the configured minimum and maximum; success resets the delay. Readiness alone never refreshes printer status. A quiet healthy printer can therefore become stale and reconnect to obtain a new snapshot. This conservative behavior is intentional and may increase local reads.

## Receive limits

The accepted application message limit is configurable up to the parser's 256 KiB cap. HTTP reads count response-body bytes before retaining additional chunks, cancel on overflow and decode UTF-8 strictly. JSON parsing also limits structure and strings. Deadlines bound connection establishment and request waiting; the projected baseline contains only the selected fields.

**Native Node WebSocket assembles a message before dispatching it. Its public API supplies no receive byte cap or receive backpressure.** The WebSocket byte check bounds accepted messages and JSON parsing after assembly. It does not prove bounded native receive memory, compression expansion, pending message events or total process memory. `close()` starts a closing handshake and cannot force socket destruction through this API. Abort detaches application listeners, releases timers and ignores further events immediately; synthetic tests also check that the fixture sees its socket close. Stronger pre-buffer bounds require a separately reviewed transport decision. This checkpoint does not claim them.

## Validation scope

Targeted tests run the real Node 24 client as a bounded subprocess against an original synthetic Bun loopback HTTP/WebSocket service. Cases cover exact read-only requests, snapshot/delta merge, replay/order rejection, reconnect with reset source time, stale/offline transitions, malformed and oversized messages, request IDs, readiness, redirects, HTTP deadlines, invalid UTF-8, abort and callback failure. Each fixture owns and closes its sockets, timers and subprocess. No upstream server implementation was copied.

`bun test tests/unit/moonraker-client.test.ts --max-concurrency 1` passed 10 test groups and 202 assertions on Node 24.20.0 and Bun 1.4.2. A temporary TypeScript configuration restricted to these four new source/test files and their imports passed `tsc --noEmit`. Formatting checks passed for the five owned files. An initial full-source `tsc --noEmit` attempt failed on existing app-side `zod` resolution and its resulting implicit-`any` error; no dependency repair or full repository gate was attempted here. A short success-fixture deadline initially caused a readiness retry; success cases now use separate generous budgets while explicit timeout-fault cases retain their short deadlines.

No dependency was added. Validation reuses the existing pinned `zod@4.6.7`; its installed MIT notice is already retained in `THIRD_PARTY.md` and the existing Connector distribution rules. Node's built-in fetch/WebSocket APIs require no new runtime package.

This is synthetic component evidence only. Genuine pinned Moonraker simulator acceptance, 0015 assignment/configuration integration, printer-local authentication and end-to-end telemetry remain pending. No hardware, Docker, PostgreSQL, emulator, SSH, production service, credential changes or publication were used. The complete repository gate remains the coordinator's separately scheduled check.
