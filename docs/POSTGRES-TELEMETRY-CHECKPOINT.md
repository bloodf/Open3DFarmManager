# PostgreSQL telemetry and proof boundary review

The enrollment review reproduced two connection-close races: an in-flight lookup could issue a challenge after `discardConnection`, and proof completion could return success after the connection closed while the transaction was still completing. Both regression tests failed before the fix. The wrapper now marks outstanding operations cancelled and checks that state before proof evaluation and after the transaction returns. In-flight bookkeeping is bounded to 1000 operations and removed on settlement. Cancellation is scoped by connection; a third regression verifies another connection still completes successfully.

This does not cancel PostgreSQL I/O or keep an everlasting registry of closed connections. The trusted server transport must stop initiating operations on closed connection IDs and never reuse IDs across connection lifetimes. Challenge state remains process-local. Cancellation before resolution suppresses success but cannot undo an authorization already returned to a caller.

The disposable PostgreSQL enrollment test additionally covers a callback exception with pool recovery, a real row-lock timeout and rejection of that consumed/discarded proof after recovery. It retains the measured revoke-before-verification ordering and normal database restart coverage. Commit-response loss, power loss, backup restoration and distributed deployments remain untested.

## Durable telemetry slice

`PostgresTelemetryStore` (`apps/farm/server/storage/postgres-telemetry.ts`) connects the internal ingestion validator in `apps/farm/server/services/telemetry.ts` to an atomic PostgreSQL batch transaction. Scope comes from trusted caller context, not event JSON. The store independently validates and snapshots up to 100 events/64 KiB, acquires rows in stable event-ID order, and deduplicates by farm, agent and event ID. Equal JSONB payloads are idempotent; conflicting reuse aborts the entire transaction. Acknowledgement is returned only after commit. Database errors remain redacted. The store exposes no endpoint of its own, and no production module calls it: its only callers are under `tests/`.

The opt-in PostgreSQL script now invokes a helper that connects synthetic Moonraker parsing, the actual disk queue, ingestion validation and the database store. It simulates a lost response after successful commit, closes/reopens the queue, and verifies redelivery acknowledges the same durable row. Additional assertions cover atomic conflict rollback, concurrent identical insertion, scope isolation and durable deduplication after a real database restart. Missing trusted context never writes.

The first actual run rejected telemetry because a pre-stringified JSON parameter became a JSONB string. The database object constraint caught the error and the queue retained the event. A follow-up check on 2026-11-04 found that the installed Bun 1.4.2 lacks the `sql.json` helper described by newer documentation and types. That observation concerns Bun's own SQL tag and was recorded at the time of that run.

The store now sends the validated plain object through the JSON helper of the `postgres` driver, `tx.json(payload)`, in both the insert and the equality check at `apps/farm/server/storage/postgres-telemetry.ts:42` and `apps/farm/server/storage/postgres-telemetry.ts:45`. The driver is declared by `apps/farm/package.json` at 4.1.1, and its typings declare `json(value: JSONValue)`. The runtime is Node, as recorded in [NODE-POSTGRES-CHECKPOINT.md](NODE-POSTGRES-CHECKPOINT.md); that checkpoint also records the earlier `postgres` 3.4.9 pin. Actual database integration against the current driver is the compatibility gate.

The telemetry table comes from the explicit migration `infra/db/migrations/0002_telemetry_events.up.sql`, with its down file, ; `0016_telemetry_operation_proofs` also references it. This store does not run migrations. It is internal persistence, not authenticated telemetry: synthetic trusted context in the fixture is not derived from enrollment proof, and the store deliberately does not interpret enrollment state. Connecting proof and channel identity to current farm and printer permission checks is still required before this store is exposed.

## Current state

The production route writes to the same table through a different class.

`apps/farm/server/api/connector/telemetry.post.ts` and `apps/farm/server/api/connector/telemetry/challenge.post.ts` declare the two Nitro routes. The handler `createTelemetryHttpHandler` in `apps/farm/server/services/telemetry-http.ts:24` requires a bearer token and the `x-connector-farm` and `x-connector-agent` headers, then calls `issueTelemetryChallenge` or `commitTelemetryWithProof` on `PostgresConnectorCredentialAcceptance` (`apps/farm/server/storage/postgres-connector-credential-acceptance.ts`, see `telemetry-http.ts:110-111`). That class checks the credential, the proof lifetime and the live printer assignment rows, then writes the whole batch with one set-based statement: `save.json(batch)` at `apps/farm/server/storage/postgres-connector-credential-acceptance.ts:649` feeds an `INSERT ... SELECT ... ON CONFLICT DO NOTHING` at line 655, and line 657 compares each stored payload with the submitted one under `FOR SHARE`, all inside the same transaction.

The production route never calls `ingestTelemetry` or `PostgresTelemetryStore`. Both symbols exist in the tree and every call site sits under `tests/`. The runtime stays inactive until `connectorTelemetry` is enabled in the Nuxt runtime configuration; `apps/farm/nuxt.config.ts` ships `connectorTelemetry.enabled: false`, so both routes answer 503 while no handler is installed.

Event retention and a storage quota are not implemented, and batch resource bounds do not bound lifetime database growth. The production runtime requires the dedicated `farm_connector_telemetry_writer` role. `createTelemetryHttpRuntime` in `apps/farm/server/services/telemetry-http-runtime.ts` throws unless the connecting role is a member of that writer role, holds no superuser, createdb, createrole, replication or bypassrls attribute, is a member of no role other than itself, the writer and the credential-acceptor roles, and owns no database or `farm` object. The table's integrity depends on restricted write roles; this slice does not defend against privileged direct SQL changes. Offline authorization policy is unchanged. No production service or device is accessed by the verification recorded below.

## Measured validation

The evidence in this section belongs to the 2026-11-04 run. The counts and results describe that commit, not the current tree.

On 2026-11-04 the expanded initial and post-restart phases both exited 0 against native ARM64 PostgreSQL 17.11, image `postgres@sha256:266d3c257594e195b309ae9d1805e54c788f1d7b375f56bf6c367aac6c917e7b`, using Bun 1.4.2. The final run verified the plain-object encoding used at that time, queue recovery, conflict rollback, concurrency, scoped deduplication and persistence across normal database restart. Two earlier integration failures remain in local evidence rather than being counted as passes.

Each attempt used a separate labeled container, volume and bridge network; publication was loopback-only, with UID 70, all capabilities dropped, no-new-privileges, 1 CPU, 512 MiB and 128 PIDs. Synthetic passwordless trust existed only in these disposable fixtures, never in project runtime configuration. The bridge did not enforce outbound filtering. All task-owned resources and newly pulled unused images were removed after each attempt, and label-filtered cleanup inventories were empty. Pre-existing containers were preserved.

Final verification for that dated run: 173 Bun tests, 95 Node tests, lint, typecheck and Connector/Nuxt builds. PostgreSQL integration is a separate explicit test, not part of these counts or CI. These counts belong to the 2026-11-04 slice and do not describe the current tree. No endpoints, production changes or publication were introduced; GitHub Actions authorization remains pending.
