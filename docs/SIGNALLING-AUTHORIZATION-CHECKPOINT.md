# Passive signalling authorization checkpoint

Status: SOURCE PREPARED. Migration 0017, SQL privileges, real PostgreSQL denial/expiry/race behavior, actual restart and migration down/up have **not run**. No runtime or socket uses this reader. Commands remain disabled. Focused strict TypeScript and two policy tests under Node and Bun passed; these do not validate SQL behavior.

The maintained `PostgresSessionRepository.authorizeAndTouch` locks account then session, evaluates session state and records expiry, but also renews activity on success. Inventory authorization also renews activity. This slice keeps those APIs unchanged and reuses their `evaluateSession` policy validation in a new passive reader.

Migration 0017 prepares `farm.observe_signalling_session_expiry(text)`. The expiry-only function accepts only the internal session ID. It accepts no clock, timeout, account identity or revocation timestamp. It samples PostgreSQL time before locks and after account SHARE → session UPDATE acquisition, uses the greater sample, checks the immutable account binding, returns no successful observation unless both exact binding locks are held, and may write only a currently expired session's `revoked_at`. It never renews `last_seen_at`. Existing revocation tombstones remain unchanged. Its definer search path explicitly places `pg_temp` last, scalar types are schema-qualified, all domain objects are schema-qualified, PUBLIC execute is revoked, and only the new dedicated reader receives execute permission. A separate NOLOGIN owner has only account/session SELECT, immutable account-ID row-lock permission and session expiry-column UPDATE. The reader cannot assume that owner role. Schema CREATE is granted only for the atomic owner transfer and immediately revoked. A caller cannot use an invented future timestamp to revoke a live session.

The function's idle policy is explicitly coupled to the maintained login runtime's 30-minute policy. The reader rejects any different configured timeout, and a focused drift test checks the maintained runtime and migration literal. Changing login policy requires a reviewed migration and reader update. This is an explicit compatibility constraint, not a dynamically configured SQL policy.

The reader locks account → session through the function, then membership → approved browser key → approved enrollment → issued credential. It reads Connector revocation metadata while holding the enrollment and credential locks. It verifies real P-256/Ed25519 key labels, exact farm/account/browser-key identity, current session/account versions, current membership, enrollment status and issued issuer/audience/fingerprint/thumbprint. It calls the expiry boundary again after later lock waits and key validation, then re-evaluates the session. The snapshot's maximum lifetime is the minimum of absolute session expiry, unchanged last activity plus configured idle timeout, and credential expiry.

Authorization denial returns normally from the transaction so any observed session expiry commits. A storage or commit failure returns `storage-unavailable`; it does not claim that an expiry tombstone persisted. No generic transaction callback or reusable socket-authorized flag is exposed. The coordinator must still perform fresh browser/Connector admission proofs, enforce its finite local lifetime and revalidate current state.

The role has no session touch or arbitrary revoke permission, no browser approval, no enrollment mutation, no credential issuance, no proof mutation and no telemetry write. Membership, browser-key, enrollment and credential row-lock privileges use identity-only UPDATE columns. Prepared real SQL negative tests must demonstrate that their lifecycle triggers reject actual identity updates, including a credential no-op update; this has not yet been executed. Function-owned account/session locks do not require caller UPDATE grants on those tables.

Prepared acceptance uses the official contiguous migration journal through 0017 in a separately owned disposable cluster. It covers exact approved identity without touching activity, wrong farm/key/agent, restricted role and PUBLIC permissions, live-session non-revocation, absolute/idle expiry committed on denial, a regressed application clock against DB-owned time, proven account and later membership lock waits crossing actual expiry, and reader-before-session-revocation contention. The restart fixture contains only synthetic identifiers and a tombstone timestamp, never a JWT or key. A new process after an actual PostgreSQL restart must still deny that expired session. SQL time is deliberately not injectable; these tests do not claim to alter the host/database clock.

The migration down removes only the new capability and role. It retains all session expiry tombstones in the maintained session store. No original fixture journal will be edited or backfilled. No PostgreSQL resource has been created by this slice while the database window belongs to other work.

Independent source review identified implicit temporary-schema type lookup in the initial prepared function; root fixed the path and scalar types before any application. A prepared fresh-backend regression creates a malicious `pg_temp.text` domain with a harmless effective-user callback, proves the callback executes as the reader on a manual cast, then requires zero callback executions inside the definer function. Effective owner flags, search path, grants, reader-to-owner escalation and DDL denial are asserted. This SQL regression remains UNRUN until the assigned acceptance window. Race fixtures now prove sessions are still live when contention is observed, and all started race promises are drained in cleanup even when assertions fail.
