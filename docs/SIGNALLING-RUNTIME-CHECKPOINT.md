# Authenticated signalling runtime checkpoint

Status: source prepared. The Node server routes now connect the maintained login, current SQL authority reader, fresh browser/Connector possession proofs, and bounded read-only signalling coordinator. Actual generated-listener HTTPS, PostgreSQL runtime, and browser-to-native-Connector integration acceptance remain pending. Commands are disabled for every identity.

## Activation and lifecycle

The local Nuxt module defaults `connectorSignalling.enabled` to false and does not enable Nitro WebSockets without an explicit literal build opt-in. Runtime enablement cannot replace that build decision. Enabled builds support only the `node-server` preset. A build that opted in retains the native limits even when runtime configuration disables admissions; removing its compiled adapter requires a rebuild.

Private enabled configuration requires `origin`, `issuer`, `audience`, `readerDatabaseUrl`, `proofDatabaseUrl`, `publicKeyRegistryPath`, `tokenTtlSeconds` (1–3600), and `proofTtlMs` (1–8000). The origin must match the maintained own-login HTTPS origin. Both dedicated database URLs must name the same endpoint/database with separate restricted logins. Startup also compares their actual server address, port, and database. The reader must inherit only `farm_signalling_reader`; the proof pool only `farm_connector_credential_acceptor`. Owner, administrative, unrelated inherited roles, and farm schema/table ownership reject activation. No SQL role or grant is added.

Pinned Nitro 2.13.6 calls plugins without awaiting their returned promises. The plugin therefore validates configuration and installs native limits synchronously; invalid configuration throws at startup. Public-key loading and SQL-role checks run before the runtime is published. Pending or failed validation leaves every upgrade unavailable, closes owned pools on failure, and captures only a generic startup error. Shutdown invalidates admissions before draining pending initialization and closing pools. There is no signalling readiness endpoint, and overall application health must not be interpreted as successful signalling initialization.

The public-key registry uses the existing bounded, regular-file, no-symlink verification-key loader. Credentials and JWTs are never placed in URLs, protocols, database rows, or diagnostic output by this runtime. Deployment TLS termination and clients using WSS remain required; the configured HTTPS origin does not prove that a raw backend socket used TLS.

## Socket boundary and resource controls

Routes are `/api/signalling/browser` and `/api/signalling/connector`, using exactly `open3dfarm.signalling.v1`. H3's WebSocket resolver bypasses ordinary HTTP handlers, so each upgrade explicitly inspects the original Node request. A synchronous global CrossWS upgrade hook rejects every other raw path before route resolution, including ordinary HTTP paths and query/trailing-slash variants. Resolved routes must provide an admission hook; absent hooks return 503 and thrown admission errors return a generic 403 through CrossWS's response-and-close path. Previously configured global hooks are rejected rather than composed with unknown admission behavior. The route boundary rejects duplicate headers, unsupported adapters, and alternate authentication carriers. Browser upgrades require the configured Origin and the maintained sealed host-only cookie. Machine upgrades reject cookies and Origin. Rejected upgrades end their sockets without a custom outer listener catcher.

Before native adapter construction, the synchronous plugin sets `maxPayload: 12288`, `perMessageDeflate: false`, and `autoPong: false`. Each socket-open hook synchronously installs the native ping termination guard before asynchronous work. The pinned Node binary-message guard closes before application processing. Unsupported native buffering or control policy closes the connection. Terminal signalling uses native termination, normally observed by a client as close code 1006, without an automatic heartbeat or reconnection policy.

The resource controller bounds pending upgrade/auth admissions to 16, socket handles to 64, processing awaits to 32, and frames to eight including the active processor. Queued plus in-flight plus native outbound bytes are bounded to 32 KiB per socket. Disconnects retain processing capacity until outstanding work settles; late results cannot reopen a connection. The coordinator separately bounds authority reads and cryptographic work. Its relay completion promise holds the socket's in-flight accounting through SQL checks and SDP hashing. Connector inboxes are capped at 16, one per agent, with one context per inbox.

## Admission and relay

The shared `signalling-socket.ts` protocol supplies strict client/server decoders and encoders with the same 12 KiB UTF-8/JSON-escaping bound. Only existing strict offer, answer, ICE, and close metadata may be relayed. Backend commands, live status, camera payloads, arbitrary data frames, TURN, and HTTP command fallback are not introduced.

1. A machine sends `connector.begin` with agent/farm/jti and JWT. The jti is an untrusted lookup hint. The current reader checks exact approved enrollment, immutable key binding, issued metadata, issuer/audience, expiry, and revocation. A fresh 0014 `signalling` challenge uses a server-generated inbox UUID. JWT alone cannot register an inbox.
2. The machine signs the entire challenge with its existing Ed25519 identity. Only fresh proof acceptance followed by current-state and expiry checks publishes `connector.inbox-ready`. Its `inbox_id` must equal the pinned first challenge's `connection_id`.
3. A browser sends `browser.begin` with farm/agent/key IDs; its session record ID comes only from the sealed cookie. The 0017 no-touch reader performs maintained session expiry authorization, current membership/key checks, and enrollment/credential checks. The coordinator returns a fresh P-256 browser transport challenge with another server UUID.
4. After the browser proves possession, the server selects the exact authenticated inbox and sends `connector.context-request`. Its `transport_id` is distinct from the inbox UUID. Its `expires_at` is the original context admission deadline, not an authority renewal.
5. The machine sends `connector.attach` with its JWT and receives a second fresh 0014 challenge bound to that transport UUID. The later challenge's generation must exceed the observed inbox generation; it need not equal generation plus one because telemetry shares the proof slot. Generation is not provisioned credential metadata. Clients pin the whole challenge per phase and independently derive their Ed25519 key thumbprint.
6. Before a challenge is pinned, a busy issuance response exposes a bounded retry delay. `connector.retry` retries the same server-owned context and original deadline. There is no automatic renewal, context replacement, or replay of an earlier proof. After a challenge is pinned, no client retry message is sent during completion. Because 0014 also throttles completion by 1000 ms, the server retains the exact frozen challenge/signature and performs at most two internal retries only for a definite busy result, within the original deadline. Abort cancels its wait; storage uncertainty, exhausted attempts, invalid proof, and expiry terminate without reissuance or commit retry. Wrong phase or early client retry also terminates the connection.
7. After both context proofs and current SQL revalidation, `rtc.ready` starts the metadata exchange. The Connector offers and browser answers. The coordinator binds the exact transmitted SDP hashes and SHA-256 DTLS pins into a strict immutable `rtc.binding`, with `commands_enabled: false`. Endpoint clients resolve their one-shot `admittedBinding` only from the exact authenticated context; received RTC proofs never supply that authority.

All admissions must finish within eight seconds. The inbox's 30-second lifetime starts before upgrade unsealing/begin. Context lifetime is the minimum of that original inbox lifetime, the original browser context lifetime, and current SQL authority. No later ready/binding message or peer construction resets these anchors. Native/browser clients must start their own timers before admission, check deadlines after async work, and close their RTC peer on signalling loss. Their own RTC possession proofs and actual DTLS certificate/description checks remain mandatory.

## Clock and revocation policy

The reader returns an explicit DB-time snapshot. Its local monotonic budget begins before the transaction and ends after COMMIT; the entire elapsed duration is subtracted conservatively. Wire issuance uses the final DB observation, with raw authority expiry as a ceiling. There is no raw-time fallback in the coordinator. Revalidation only shortens the original deadline; observed local wall/monotonic regression or discontinuity closes the connection.

This prototype requires synchronized clocks: DB observations must fit the single request wall interval with a 250 ms skew guard. Endpoints use one request interval, without a second RTT allowance or expiry grace. Legitimately skewed hosts can be denied. This does not claim detection of unobserved DB clock rollback. Session expiry remains durable through the maintained guarded 0017 function and commits on denial.

Every relayed operation rereads current browser/session/farm/key/enrollment/credential authority. Periodic five-second checks cover idle contexts and Connector inboxes. Current Connector reads lock enrollment before credential, matching proof acceptance/revocation ordering. The client must fail closed if it cannot enforce its local lifetime. An offline endpoint cannot learn remote revocation immediately; its fixed local deadline remains the upper bound. No physical printer stop or other automatic command is performed.
