## Creality stock LAN: evidence and gaps

2026-11-25. Everything below is simulator evidence from reference-derived fixtures. Nothing was captured from or run on a printer, and the catalog rows stay unqualified. Wire facts only; no vendor code is copied.

- **M** (maker): [CrealityPrint `6262848e`](https://github.com/CrealityOfficial/CrealityPrint/tree/6262848e302b8c0d593f2b341cd01310aa2f58a1), AGPL-3.0. The device UI is the compiled bundle `resources/web/deviceMgr/assets/D-MKTaRJ.js`.
- **H** (client): [ha_creality_ws `58c00818`](https://github.com/3dg1luk43/ha_creality_ws/tree/58c00818e8303a0d636bd05929cad215aed9ccb3), AGPL-3.0.

### Files

Tests: `tests/node/creality-file-journeys.test.ts`, `tests/journey/creality.spec.ts`, `tests/journey/creality-secure.spec.ts`.

- A failed listing records its earliest cause in the Connector log (`file-list-failed`, with `reason` and `requestSent`): `unauthorized`, `cancelled`, `timeout`, `endpoint`, `connect`, `closed`, `reply-invalid` or `ambiguous-names`. The browser still receives `offline`: the wire reason list is closed, and `unsupported` would let the page start a typed file name.
- Nothing is uploaded or commanded when the listing fails. A `start_print` sent by name through the integration API is not preceded by a listing.
- A secure printer is uploaded to over HTTPS on `httpsPort` (default 443), as M does in `Device/Klipper4408Interface.cpp`. An endpoint that cannot be verified is refused, never downgraded.
- **Unproven:** M checks the printer's certificate against its bundled CA but skips the host name and the certificate dates. The Connector checks both, so a real secure printer may be refused even with the right `caFile`.
- **Journey finding:** since `d822e386` the issuer grants only controls advertised by telemetry in the last two minutes. The Creality journeys kept telemetry upload closed, so `POST /api/pause-authority/capabilities` returned 403 and the page failed before any request reached the Connector or the printer. Both specs now keep upload open. With it open, the live session dropped once in four runs of the stock journey, at the cancel step.

Maker mode "Stable" (50) has no shared level. A printer that does not report `speedMode` gets `setFeedratePct` alone. Speed is refused while `sleepMode` is 1, and on model `F022` unless it is printing.

### CFS load and unload

Tests: `tests/node/creality-speed-cfs.test.ts`. Source: M device UI (`feedInOrOut`, `feedstate`), H for `get boxsInfo` and the `selected` slot.

- Off by default. The owner enables it per printer with `"cfsFeed": true` in the Creality binding, because it heats and moves filament and has not been run on hardware.
- `{"feedInOrOut":{"boxId","materialId","isFeed"}}`, sent only when idle, `feedState` is 0, 3, 14 or 100 and the slots were just read. Load takes `tray` 0-15 (four per CFS unit, units in ascending box id) and needs a slot with a filament type. Unload retracts the single `selected` slot.
- Confirmation is `feedState` 3 (fed) or 14 (retracted). A real feed takes longer than the command wait, so expect an unknown result.
- **Gaps:** external spool holders; models `F022` and `F039` (refused); the farm page's tray picker does not recognise Creality slot ids (`box:slot`), so a load from the page is refused (`invalid-command`) while unload works; the farm catalog still marks Creality materials unsupported.

### Not implemented

- **K3 nozzle mapping.** M's device UI reads `nozzleList`, `nozzleState` and `nozzleFilament` and sends `loadNozzle` for model `F039`, but no pinned source ties `F039` to the K3 or shows how a job's tools are mapped to nozzles at print start. Nothing is sent.
- **Multi-colour start.** M sends `colorMatch` and then `multiColorPrint` for CFS jobs; OpenFarm starts files with `opGcodeFile` only.
