## Summary

Keep the OpenFarm Connector and its command boundary. Adopt sourced catalog data, selected printer workflows and simulator scenarios. FullFarmManager has a Stage 1 Go simulator, a Next.js prototype and a useful job/run model. The snapshot does not provide real drivers or successful web integration checks. OpenFarm's baseline stays Klipper/Moonraker and Spoolman, with additional driver support graded by model, firmware and capability.

Commercial orders, products and BOM, purchasing, finance, staff and general supplies are **Cofre3D** (bloodf/cofre3d). The review covers material and consumable tracking only where it affects printer operation.

## Risks

- Protocol family names and vendor LAN workflows can hide firmware, authentication and camera differences. Record provenance and qualification per capability. Treat simulated payloads as test data.
- A successful upload or acknowledgement can precede a failed or uncertain start. Correlate with observed state and expose uncertainty without retrying. Duplicate and delayed events must not advance a plate or debit stock twice.
- Pending work can outlive authority or become unsafe when the bed, consumables or printer state changes. Admission belongs in the Connector at execution time. API commands require owner-granted scope and issuer signatures. Browser commands use WebRTC only, without TURN or HTTP fallback.
- Resin levels and usage are often unavailable. Preserve unknown values and distinguish measurements from manual entries and estimates. Never apply FDM safety or command assumptions to a resin device.
- Use original implementation and fixtures with documented provenance. Check dependency licenses and retain required notices.

## Driver matrix

The owner's 2026-11-22 order calls for a real Connector driver for every catalog printer and every maker-documented control that its firmware exposes. New model, firmware, mode and accessory combinations remain hardware-unqualified until the owner runs them. Existing hardware evidence retains its original scope. Sources were checked on 2026-11-22. The [FDM catalog](catalog-fdm.md) and [resin catalog](catalog-resin.md) supply individual maker specifications and manuals.

**E** exists in OpenFarm within the stated scope. Generic and family-level entries describe reusable implementation and do not establish per-model compatibility. **D** is documented by a maker or its board/firmware supplier and is a build candidate. **N** means the cited maker workflow explicitly excludes the capability in the stated configuration. **?** means the reviewed sources leave the capability unverified. A maker UI or file-transfer workflow can establish that a feature exists as a product feature. A **?** remains where the wire contract or the firmware's support for it is unknown. A documented family protocol marked **D** on a candidate row is conditional on matching that protocol on the named firmware.

Discovery covers enumeration or identification at a configured address. Connection covers transport and authentication where provided. T/F includes temperature and fan observations and writes, which are distinguished in the cells. Consumption means printer telemetry or estimates with provenance. History distinguishes maker history from OpenFarm's observed runs. Multi-material includes feeders, slots, tools and their controls.

### Evidence and implementation scope

- **B · Bambu.** Check port, mode and authorization tables before enabling controls. Developer Mode and authorized Bambu Connect are different operating modes. The maker describes control categories and channels without a complete public MQTT command schema. The OpenFarm LAN adapter in `bambu/` plus the local discovery, camera and cloud modules supplies the existing wire evidence. Bambu Studio is AGPL-3.0 and its networking plugin has separate terms. [Network ports](https://wiki.bambulab.com/en/general/printer-network-ports), [LAN mode](https://wiki.bambulab.com/en/knowledge-sharing/enable-lan-mode), [Developer Mode](https://wiki.bambulab.com/en/knowledge-sharing/enable-developer-mode), [authorization](https://wiki.bambulab.com/en/software/third-party-integration), [Bambu Studio source and plugin notice](https://github.com/bambulab/BambuStudio), [license](https://github.com/bambulab/BambuStudio/blob/master/LICENSE).
- **C · Creality FDM.** OpenFarm's `discovery/`, `creality/` and secure transport regression tests already cover secure WS in supported configurations. Qualify advertised secure endpoints and camera selection per firmware, including legacy WS models. Rooted K2 SE/Hi and stock configurations need separate evidence. Creality Print is AGPL-3.0. [Pinned official client references C1/C2](catalog-fdm.md#protocol-references), [client and license](https://github.com/CrealityOfficial/CrealityPrint), [SPARKX maker Moonraker statement](https://www.creality.com/blog/sparkx-open-initiative).
- **H · Creality HALOT.** Creality documents the HALOT workflows separately. There is no HALOT-specific Connector adapter. Treat the X1 and MAGE generations as independent protocol candidates. [HALOT maker guides](https://wiki.creality.com/en/halot-series), [model-specific sources](catalog-resin.md).
- **A · Anycubic FDM.** `kobra-x/`, `kobralink/` and `anycubic/` cover distinct paths. The common command builder gates on model code `20024`. The maker's Kobra X LAN workflow documents jobs, progress and video, with cloud/app disconnected in LAN mode. It supplies no protocol guarantee for Kobra 4, 3 Max V2 or S1 Max. [Maker LAN guide](https://wiki.anycubic.com/en/fdm-3d-printer/anycubic-kobra-x/lan-connection-guide), [other FDM model sources](catalog-fdm.md).
- **P · Photon.** The Photon Workshop LAN workflow and P1 guide establish vendor workflows. Obtain a supported API or versioned wire evidence before implementing writes. M3 Max is scoped to the documented USB Type-A workflow. [P1 LAN guide](https://wiki.anycubic.com/en/resin-3d-printer/anycubic-photon-p1/lan-connection-guide), [Workshop manual, M7 Max availability and model-specific maker sources](catalog-resin.md#protocol-evidence), [M3 Max specification in catalog](catalog-resin.md).
- **E · Elegoo.** Existing `sdcp/`, `discovery/sdcp.ts`, collection and simulator cover v3 discovery and status. CBD-Tech documents actions 128–131, video, multipart transfer, task detail/history, layer volume and alarms. Apply them only after a specific firmware identifies as compatible. Centauri LAN setup does not establish CBD-Tech v3 compatibility. The Saturn 2 and Mars 3 Pro entries use the maker's USB-only specifications. No third-party client is used for this evidence. [CBD-Tech v3 specification](https://github.com/cbd-tech/SDCP-Smart-Device-Control-Protocol-V3.0.0/blob/main/SDCP%28Smart%20Device%20Control%20Protocol%29_V3.0.0_EN.md), [Centauri Carbon connection](https://wiki.elegoo.com/en/Centauri-carbon/connection), [Carbon 2 Combo FAQ](https://wiki.elegoo.com/en/faq/centauri-carbon-2-combo), [Elegoo resin maker sources](catalog-resin.md).
- **S · Snapmaker.** The official fork establishes Moonraker on U1. Current `moonraker/u1-tools.ts` and command gates provide four tool identities and refuse writes for a declared U1. The driver target adds verified write capabilities individually through the existing admission path. Snapmaker's Moonraker fork and Klipper firmware are GPL-3.0 references. [Maker firmware announcement](https://blog.snapmaker.com/blog/snapmaker-u1-firmware-now-on-github/), [Moonraker fork](https://github.com/Snapmaker/u1-moonraker), [U1 Klipper fork](https://github.com/Snapmaker/u1-klipper).
- **M · Moonraker.** Existing `moonraker/`, discovery, files and control cover the generic protocol. Optional history, cameras, telemetry objects and approved macros depend on host configuration. Moonraker is GPL-3.0 and exposes official API documentation. [Printer operations](https://moonraker.readthedocs.io/en/latest/external_api/printer/), [API docs including files, authorization, webcam and history](https://github.com/Arksine/moonraker/tree/master/docs/external_api), [source and license](https://github.com/Arksine/moonraker).
- **R · Prusa.** No dedicated Connector PrusaLink adapter. Use the maker's AGPLv3 PrusaLink Web specification and generation-specific firmware evidence. Local job state and Prusa Connect production history are different data sources. [Official OpenAPI](https://github.com/prusa3d/Prusa-Link-Web/blob/master/spec/openapi.yaml), [8-bit host releases](https://github.com/prusa3d/Prusa-Link/releases), [Buddy firmware including filament endpoint releases](https://github.com/prusa3d/Prusa-Firmware-Buddy/releases).
- **Q · Qidi.** Reuse generic Moonraker code. Start with Q2 and prove endpoint parity for each additional generation. Qidi's Moonraker fork is a GPL-3.0 firmware-side reference. [Q2 firmware](https://github.com/QIDITECH/QIDI_Q2), [Moonraker fork](https://github.com/QIDITECH/moonraker).
- **F · Flashforge.** No dedicated Connector adapter. Maker LAN workflows establish network job delivery and UI capability. The mobile app requires internet and the base 5M camera is optional. Establish stock-firmware wire behavior separately by model. [5M manual](https://wiki.flashforge.com/resource/adventurer_series_manual/adventurer_5m_manual.pdf), [Orca-Flashforge workflow](https://www.flashforge.com/a/docs/preview/layout_1/orca-flashforge/orca-flashforge-quick-start-guide), [camera and app limits](https://wiki.flashforge.com/en/Flash-Studio/Flash-Studio-Mobile/FAQ).
- **V · Sovol.** Use generic Moonraker with model-specific capabilities. The SV08 and SV08 Max sources provide firmware and host configuration evidence. Evaluate other Klipper machines only where Moonraker is actually exposed. [SV08 official repository](https://github.com/Sovol3d/SV08), [SV08 Max Moonraker sources](https://github.com/Sovol3d/SV08MAX/tree/main/home/sovol/moonraker).
- **Z · Phrozen.** No dedicated Connector adapter. Treat Phrozen GO and same-LAN imports as maker workflows pending a local API contract. The Mini 8K S uses USB-only input in the maker specification. [Maker sources per Phrozen model](catalog-resin.md).
- **L · Formlabs.** `formlabs/`, collection and simulator currently implement v0.9.11 device listing/status for Form 4/4L. PreForm v1 alpha documents scene upload and `print_now`. Explicit queue-only submission and immediate printing must remain distinct operations. Check `/v1/print-setting/list/` and device identity before enabling Studio 1. Dashboard is a separate cloud boundary. [v0.9.11 reference](https://formlabs-dashboard-api-resources.s3.us-east-1.amazonaws.com/formlabs-local-api-v0.9.11.html), [PreForm v1 API](https://developer.formlabs.com/api-reference/), [explicit queue/print behavior](https://developer.formlabs.com/getting-started/quickstart/), [priming and start requirements](https://formlabs.com/support/Starting-a-remote-print/).

## Driver fan-out

**Ownership:** Bambu, Creality FDM, Anycubic FDM, Snapmaker and Klipper-based drivers belong to the openfarm-fdm team. Elegoo, Phrozen, Formlabs, Anycubic resin, Creality HALOT, Prusa, Qidi, Flashforge and other brands belong to openfarm-drivers. Shared driver interfaces, catalog schema and Connector core belong to this repository's core team.

Build in the order below. Rows with incomplete maker wire contracts start with evidence and an offline model harness. Enable only the capabilities that the evidence supports. USB-only models can use explicit offline records and manual file handoff. Size is relative implementation effort for each family.

Every unit uses original code and simulated or fixture-backed tests. Start each fixture with `recorded` and its source, or `spec-derived, not captured` and its doc URL. No automated test contacts a physical printer. Keep existing hardware-path tests green. Owner hardware runs qualify each model/firmware/capability over and above simulator acceptance.

Each write acceptance case exercises Connector admission, approved state, a refused unauthorized or unsafe request with a reason, an ambiguous result without a second send, and recovery in read-only degraded mode. Browser live status, camera and commands use browser-to-Connector WebRTC, with no TURN or HTTP command fallback. Integration API actions require an owner-granted scope and issuer-signed envelopes under the [Integration API](../INTEGRATION-API.md) and [OpenAPI contract](../api/openapi-v1.yaml). Keep authority checks, interlocks and uncertainty in the Connector during outages without opening inbound ports. Use existing persistence and Spoolman fields. Preserve unknown readings and mark estimates. See [ADR-001](ADR-001-lan-agent.md).
