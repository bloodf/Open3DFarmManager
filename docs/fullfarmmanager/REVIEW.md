## Simulated status journeys — 2026-11-23

RTC journey regression diagnosis. After `bfcb7cd8` was merged, the run at `f708f89a` failed Qidi because it never reached authenticated direct status, and a retry failed Flashforge. The merge did not cause this. The same internal-bridge runner reproduced the failure on the pre-merge commit `2bc65c1f`, where all three journeys failed, and on `f708f89a`, where Flashforge and Qidi failed and Phrozen passed. Both commits contain the detail-page assertions from `737ed3e5`. Those assertions keep a second tab open on the printer detail page, and that tab runs its own read-only signalling session. The browser signalling traces show the problem. Whichever tab first gets `rtc.ready`, `rtc.answer` and `rtc.binding` holds the Connector's single read-only inbox. While it does, the server closes every `browser.proof` from the other tab within about 5 ms. This matches the `Connector unavailable` path in `signalling-runtime.ts`, which requires the inbox to be in `connector.ready`. When the detail tab wins, the farm row never reaches authenticated status. The passing run at `61d13310` was a race that the farm tab happened to win. The journey now shows the farm row, inspector and detail page one after another on a single page. It checks each surface while that surface holds the direct connection, and it checks the detail page only after it shows `Connector: conexão direta ativa` with the expected state. The request-set, stale-data and recovery assertions are unchanged. That version attached browser signalling and runtime logs on failure. With this change applied to `996b6de9`, Qidi, Flashforge and Phrozen passed 3 of 3 with zero skipped in each of three consecutive runs on the same runner. Product follow-up, not changed here: the Connector serves one read-only browser link at a time, so a second open farm or detail tab for the same Connector fails closed and retries instead of sharing the link. The earlier diagnostic attachments included raw runtime logs; the current journey retains only fixed protocol tags and event counts.

## Summary

Keep the OpenFarm Connector and its command boundary. Adopt sourced catalog data, selected printer workflows and simulator scenarios. FullFarmManager has a Stage 1 Go simulator, a Next.js prototype and a useful job/run model. The snapshot does not provide real drivers or successful web integration checks. OpenFarm's baseline stays Klipper/Moonraker and Spoolman, with additional driver support graded by model, firmware and capability.

Commercial orders, products and BOM, purchasing, finance, staff and general supplies are **Cofre3D** (bloodf/cofre3d). The review covers material and consumable tracking only where it affects printer operation.

## Risks

- Protocol family names and vendor LAN workflows can hide firmware, authentication and camera differences. Record provenance and qualification per capability. Treat simulated payloads as test data.
- A successful upload or acknowledgement can precede a failed or uncertain start. Correlate with observed state and expose uncertainty without retrying. Duplicate and delayed events must not advance a plate or debit stock twice.
- Pending work can outlive authority or become unsafe when the bed, consumables or printer state changes. Admission belongs in the Connector at execution time. API commands require owner-granted scope and issuer signatures. Browser commands use WebRTC only, without TURN or HTTP fallback.
- Resin levels and usage are often unavailable. Preserve unknown values and distinguish measurements from manual entries and estimates. Never apply FDM safety or command assumptions to a resin device.
- Use original implementation and fixtures with documented provenance. Check dependency licenses and retain required notices.
