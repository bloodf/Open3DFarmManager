# Creality stock LAN commands: sources for unsupported actions

This reference records source evidence for issue #236. The OpenFarm file-listing implementation is covered by a simulator. No OpenFarm test in this reference used a physical printer.

Scope: the Creality stock WebSocket on port 9999 and the stock HTTP upload. The "Repo status" column refers to `packages/connector/src/creality/commands.ts` and `files.ts` on this branch.

## Concerns

- **`run_macro` is not in the UI's known list.** `apps/farm/app/utils/farm-control-extended.ts` builds "unsupported" from `extendedActions` plus the two filament actions, so `run_macro` never appears as "Não suportado" for any vendor, although issue #236 names it for Creality. This doc covers it anyway. Decide in a follow-up whether to add it to the UI list.
- **`set_speed` and CFS feed follow the maker device UI**, pinned in [DRIVER-EVIDENCE.md](../fullfarmmanager/DRIVER-EVIDENCE.md#creality-stock-lan-evidence-and-gaps). Neither has a hardware capture.
- **Erinell's repository has no license.** It is cited for wire facts only. Its `deleteGcodeFile` sends `{"stop":1}`, not a delete, so it is not used as a source for deletion.

## Browser file listing

An authorized browser file-list request reaches the Connector over the existing WebRTC channel. The Connector opens the provisioned printer WebSocket and sends one `{"method":"get","params":{"reqGcodeFile":1}}` request. It reads `retGcodeFileInfo2` from the reply, using the entry's `name`, `path`, and `size`. [Stock LAN request, response, and K2 Plus observations](https://github.com/Accessible3D-Edis/AccessSlice/blob/620e023e5425137c58353ffa6974c260b103d134/app/creality_lan.py#L17-L24)

The adapter accepts flat `.gcode` files under `/usr/data/printer_data/gcodes` and `/mnt/UDISK/printer_data/gcodes`. The file entry carries a Connector reference when the start command needs the UDISK path. Duplicate names across those two directories make the list ambiguous and are refused. The existing start confirmation and Connector safety checks apply.

The simulated browser journey checks `Nenhum arquivo nesta impressora.` for an empty list, then uploads a file and checks `Arquivos atualizados.` plus the file option. A confirmed start sends one `opGcodeFile` frame with the reported UDISK path. The browser reports an unknown command result, and the simulated job subsequently appears as completed in history.

### Rollout order

The existing file channel has no browser parser version negotiation. Browsers from before the parser change reject an entire listing response containing a `creality-udisk:` reference. The parser-only change accepts the existing replies and the new reference.

1. Deploy the farm browser build from the parser-only change first. Verify the served release contains that change and refresh or retire sessions using older browser bundles.
2. Release the Connector listing change only after browsers that can reach it load the updated parser. Verify a fresh browser can list and select a UDISK file against a simulator.
3. If rolling back both releases, roll back the Connector first so it stops emitting the new reference before restoring the older browser parser.
