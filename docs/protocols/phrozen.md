# Phrozen resin

The Connector candidate probes a provisioned IPv4 address with SDCP v3 discovery over UDP 3000. It checks the source address and port and requires the exact SDCP `MachineName` value `Sonic Mighty Revo 14K`, V138 or V153 firmware, and an explicit `V3.0.0` reply. Discovery rejects the generic `Sonic Mighty Revo` name because it does not establish the 14K variant. Firmware and model names in replies still need confirmation on hardware. It ignores advertised addresses and connects to the provisioned address at TCP 3030, `/websocket`. The LAN protocol has no authentication or encryption. Reply checks correlate the endpoint, board and request. Use only on a trusted local network. [CBD SDCP v3 specification](https://github.com/cbd-tech/SDCP-Smart-Device-Control-Protocol-V3.0.0)

Control, upload, video and task resin usage are spec-derived. The runtime reaches pause, resume, stop and file transfer only for a qualified model and firmware pair, and that list ships empty; start, video and usage are not wired. Sources, refusals and gaps are in [Phrozen driver evidence](../fullfarmmanager/evidence/phrozen.md).

Each connection carries one request, except that the read-only collector keeps its status socket between polls and drops it after any failure. A status read (command 0) requires a matching success acknowledgment and a board-scoped status frame. SDCP status frames lack request IDs. The result preserves raw job state, progress, reported temperatures, print error codes and wear counters when present. Missing fields stay absent. Wear counters measure component use. Status carries no fan mapping, material identity or resin consumption, and the adapter has no alert subscription. No vendor account, retry or command fallback is used.
